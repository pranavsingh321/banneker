⚙ INFRA 4 decisions
DEC-001
How should compute orchestration be distributed across processes?
Choice
Three-process distributed architecture: nova-compute, nova-conductor, and nova-scheduler run as separate daemons communicating via RPC (oslo.messaging).
Rejected alternatives
Monolithic single-process Nova — would not scale horizontally; direct DB access creates security risks
Microservices with separate API per function — OpenStack ecosystem requires tight integration
backend
DEC-005
How should Nova scale to support thousands of compute nodes?
Choice
Cells v2 architecture: Cell0 is metadata-only; Cell1+ each have their own database, conductor, and compute hosts.
Rejected alternatives
Database partitioning — harder to manage, single point of failure for conductor
Fully distributed peer-to-peer — no centralized resource tracking or scheduling
backend
DEC-006
What concurrency model should Nova use for handling requests?
Choice
Eventlet green threads as default, with native Python threading fallback.
Asyncio — oslo.* library ecosystem is built on eventlet; migrating would require rewriting the entire dependency chain
Thread-per-request — native threads consume more memory and OS resources
backend
DEC-010
What is the messaging transport for inter-service RPC communication?
Choice
oslo.messaging with RabbitMQ via Kombu as the default transport for RPC between API, scheduler, conductor, and compute.
ZeroMQ — no message persistence; lost messages during broker restart would cause data inconsistency
Direct TCP connections — tight coupling, no message queuing semantics

▦ DATA 2 decisions
DEC-002
How should Nova manage its data models across API versions and database migrations?
Choice
Two-layer data model: SQLAlchemy ORM models with Shadow tables wrapped by oslo.versionedobjects (65 object classes).
Single ORM model layer — would require DB migrations for every API change
Flat NoSQL data store — OpenStack services expect relational data with strong consistency
backend
DEC-012
How should configuration options be organized across the codebase?
Choice
Modular config options in nova/conf/ (48 modules), aggregated via oslo.config entry point with INI-style nova.conf.
Single monolithic config file — 48+ subsystems make a single file unwieldy
YAML/JSON config — oslo.config supports existing OpenStack deployment tooling

⏶ API 2 decisions
DEC-003
What is the REST API communication strategy and versioning approach?
Choice
REST API over WSGI with microversioning (2.1 base, currently 2.104). URL routing via Routes with custom ProjectMapper. JSON-only response.
URL-based versioning (/v1/, /v2/) — creates permanent endpoints that cannot be deprecated
GraphQL API — OpenStack ecosystem uses REST; would break existing SDKs
backend
DEC-007
How should authorization be enforced across the API layer?
Choice
oslo.policy with 56 policy modules defining fine-grained RBAC rules. Custom enforcer entry point at nova.policy.
Custom authorization framework — incompatible with existing OpenStack policy tools
ABAC — oslo.policy role-based rules are simpler to manage and audit

⚬ COMPUTE 2 decisions
DEC-004
Which virtualization backend should be the default?
Choice
Libvirt (KVM/QEMU/LXC/Parallels) as default driver; VMware, IBM Z (ZVM), bare metal (Ironic) as optional Stevedore plugins.
Make all drivers first-class — bloats core with driver-specific code
Container-only runtime — VM workloads dominated cloud demand at design time
backend
DEC-009
How should privileged operations be isolated from untrusted API code?
Choice
oslo.privsep with privilege separation helpers. Privileged operations execute in a separate process via oslo-rootwrap.
Run nova-compute as unprivileged user — hypervisor operations require root
Sudo-based escalation — oslo.privsep is more secure and efficient

▲ SCHEDULING 2 decisions
DEC-008
How should Nova support pluggable scheduler filters and weight functions?
Choice
Stevedore entry points for 19 scheduler filters and weight plugins, with custom RequestFilter base class.
Hard-coded scheduler logic — would force one policy across heterogeneous deployments
External scheduler service — scheduling is latency-sensitive with placement data needs
backend
DEC-011
How should build requests be coordinated between scheduler and compute?
Choice
Scheduler → Conductor → Compute RPC chain with cursive distributed state machine for live migration and TooZ lock groups.
Direct Scheduler → Compute — bypasses conductor, losing DB consistency and cell routing
Synchronous build — blocks API threads during long-running VM provisioning
